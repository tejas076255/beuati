# BeautyFolio — Phase 3F.2B: Media SEO + Image Accessibility + Structured Media Data

Local development only. No deployment, hosting configuration, DNS, or Google Search Console action taken or required by this phase.

## 1. Existing media architecture discovered

Direct schema/RLS reads before writing any code confirmed:

- `portfolio_images` already has both `alt_text` **and** `caption`, plus `width`/`height`/`file_size_bytes`/`mime_type`/`created_at`/`is_cover`.
- `before_after_images` already has `alt_text` (no `caption` column — before/after pairs describe the transformation via the parent `before_after_items.title`/`event_type`/`description`, not per-image captions).
- `portfolio_videos` already has `title`/`description`/`category`/`thumbnail_url`/`platform`/`video_url`/`storage_path`/`duration_seconds`/`created_at`/`is_published`.
- Owner-write RLS on both image tables and `portfolio_videos` already uses the shared `owns_beautician_profile()` policy helper (confirmed in `docs/BEAUTYFOLIO-PHASE2-STEP2A-DATA-MODEL.md` §"RLS/Security"); public-read policies already gate on `is_published`.

**Conclusion: zero new database columns were needed.** The entire gap was application-layer: (a) no dashboard UI existed to set `alt_text` on an individual gallery/before-after image, and (b) the public rendering path ignored real `alt_text`/`caption` values entirely, always generating a flat `"{label} by {name}, {role} in {city}"` string via the existing `imageAlt()` helper — so even a manually-authored caption got redundant boilerplate appended on top of it.

## 5. Gallery SEO implementation

The dashboard now shows, under each uploaded photo, a "Photo description" label with helper text: *"Describe what is visible in the photo. This helps accessibility and search engines understand your work."* No mention of "SEO" or "alt attribute" anywhere in the UI copy. Saving writes to the existing `alt_text` column; clearing the field back to empty writes `null`, which hands control back to the automatic fallback.

## 6. Before & After SEO implementation

Each side of a before/after pair gets its own "Photo description" field, writing to that image row's own `alt_text`. When left blank, the two sides never receive identical wording — the fallback hierarchy always produces a "Before {subject} transformation" / "After {subject} transformation by {name}" pair, verified in manual testing (see §14).

## 7. Video/thumbnail implementation

No dashboard field was added (no schema support and none requested). Every video's public thumbnail `alt` is generated by `buildVideoThumbnailAlt()` from the video's real `title`/`category`, e.g. *"My bridal work — video by Dharti R Panchal"* — confirmed live against real uploaded video data.

## 8. Alt-text fallback logic

`src/lib/media-alt-text.ts` implements the specified tier hierarchy for every media type:
1. Manual text (`alt_text`, or `caption` for gallery images) — used verbatim, no wrapping/boilerplate appended.
2. Title + category.
3. Title + professional/service context.
4. Category + owner name + city.
5. Safe generic fallback (never the literal string `"image"`).

Before/after alt text additionally guarantees the before/after pair never matches: the "before" side never carries the professional's name (it's a plain description of the starting point); the "after" side always attributes the result to the professional.

## 9. Image performance / accessibility changes

No new image CDN, no Storage rebuild, no image-transformation pipeline was introduced (explicitly out of scope). Existing lazy-loading (`loading="lazy"` on all below-the-fold images, `loading="eager"` only on the first couple of gallery items) and existing fixed `width`/`height` attributes on every `<img>` (already sized to match each section's aspect-ratio container, preventing CLS) were confirmed intact and unmodified — this phase only changed `alt` attribute values, never markup structure, sizing, or loading strategy.

## 10. Structured data implementation

Added `ImageObject` entries (one per gallery photo, two per before/after pair) and `VideoObject` entries (one per published video) to the existing JSON-LD script in `portfolio.$slug.tsx`, via two new pure helper functions (`buildImageObjects`, `buildVideoObjects`).

Only real, already-resolved values are ever emitted:
- `contentUrl` — the actual resolved Storage/public URL.
- `name`/`caption`/`description` — the same real label/alt text used on the public page (never re-fabricated).
- `creator` — `{ "@type": "Person", "name": profile.name }`, the real profile owner.
- `dateCreated` (images) / `uploadDate` (videos) — only included when the row's real `created_at` is present.
- `thumbnailUrl` (videos) — always present (required, non-nullable on every stored video row).
- `contentUrl` (videos) — only for `platform: "uploaded"` videos with a resolved file URL.
- `embedUrl` (videos) — only for YouTube/Instagram videos where a real embeddable URL could be derived (reusing the existing `getVideoEmbedSource()` helper from the video-playback feature, with the player-only `autoplay` query stripped since structured data should point at the canonical embed, not an autoplaying one).
- `duration` (videos) — only when `duration_seconds` is present, formatted as ISO 8601 (`PT{n}S`).

No property is ever fabricated or defaulted when the underlying data doesn't exist — the property is simply omitted from that entry (e.g., a video with no `duration_seconds` gets no `duration` key at all).

Live-verified against the running dev server (`/portfolio/dharti-panchal`): 5 `ImageObject` entries and 3 `VideoObject` entries rendered, all with real Supabase Storage URLs, real captions, and real timestamps — no placeholder data anywhere in the output.

## 11. Media + ownership (RLS) verification

`updateImageAltText()` in both `gallery.server.ts` and `before-after.server.ts` performs a direct `.update(...).eq("id", imageId)` with no explicit ownership join in application code — this is consistent with, not a deviation from, the codebase's established pattern (every other owner-scoped mutation in this app relies on RLS for enforcement rather than re-implementing ownership checks client-side). Both tables' owner-write RLS policies use `owns_beautician_profile()`, confirmed already in place per the Phase 2 data-model audit — a user attempting to update an `alt_text` row they don't own is rejected by Postgres RLS before the update can apply, regardless of what `imageId` the client sends. Public portfolio reads only ever return `is_published: true` rows, unchanged by this phase.
