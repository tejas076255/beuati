## Key facts that change what gets built (verified, not assumed)

- **`lead_status` enum has exactly 6 values**: `new | contacted | qualified | booked | lost | archived`. There is **no** `converted` or `spam` value, despite the reference document suggesting those names. The existing dashboard (`dashboard.leads.tsx`) already uses all 6 values in its status dropdown. **Phase 1 admin Leads UI must reuse this exact enum — no new values added.**
- **Admin already has working RLS access to `leads`** via `owns_beautician_profile()`'s built-in `OR has_role(auth.uid(),'admin')` clause, used by all three `leads_owner_*` policies. Building `/admin/leads` requires zero RLS changes — only a new admin-facing query file and route, following the exact pattern already used for Profiles/Reviews/Services.
- **`beautician_profiles` now has `is_verified` and `is_featured` columns** (added in Step 2). The pre-existing `metrics_verified` boolean was confirmed unrelated (demo-profile stats display only) and was left untouched, not repurposed.
- **Column-level security gap found and fixed during Step 2**: `bp_owner_update`'s RLS is row-level only — an owner updating their own row would have been able to set `is_verified`/`is_featured` on themselves via a direct API call, since RLS can't restrict individual columns. Fixed with a `BEFORE INSERT OR UPDATE` trigger (`guard_beautician_profile_flags`), mirroring the exact existing pattern already used for `reviews.is_verified` (`guard_review_verification`) — not a new authorization system, the same one extended to a second table.
- **No audit table of any kind exists anywhere in the schema.** This is a genuine new addition, not a UI-missing case.
- **`bp_owner_insert`'s `WITH CHECK` has no admin OR-clause** (only the owner path) — irrelevant to Phase 1 (admin doesn't create profiles on a beautician's behalf), noted here for completeness since it was found during the audit.
