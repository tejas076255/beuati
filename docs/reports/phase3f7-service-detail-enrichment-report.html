1–2. Existing Schema Audit & Schema Decision

Queried the live services table and reviewed every repo migration before writing new SQL. No existing field captured inclusions, suitability, or preparation notes; package_services is a pure junction table with no detail columns — zero duplication risk confirmed.

Reused the exact list-column convention already established by packages.inclusions — TEXT[] NOT NULL DEFAULT '{}'::text[] (confirmed live: column_default = '{}'::text[], is_nullable = NO) — rather than inventing a second pattern (e.g. jsonb) for the same kind of data. preparation_notes is plain nullable TEXT.

3. Database Migration

20260825140000_service_detail_enrichment.sql, applied live via Lovable MCP. Adds included_items, suitable_for, preparation_notes. No RLS change needed — services_owner_all / services_public_read are row-level policies that cover new columns automatically.

5–7. What's Included / Suitable For / Preparation

  • What's Included: repeatable text-list dashboard input, rendered publicly as a checkmark list, only when non-empty
  • Suitable For: same repeatable-list pattern, rendered publicly as wrapped chip tags, only when non-empty
  • Preparation Notes: plain textarea, rendered publicly as a paragraph under "Before your appointment," only when non-null/non-empty

8–9. Dashboard UX & Validation/Default Behavior

New section placed below the Price/Duration grid, border-separated, customer-facing language only — no raw column names surfaced in the UI. All three fields start empty for new services and are never auto-populated. List items cleaned at submit (cleanListItems: trim, drop blank, dedupe case-insensitively, 120-char cap). Preparation notes trims to null when blank — never stored as an empty string.

10–12. Public Page Changes, Empty States, SSR Behavior

Live-verified via raw SSR HTML fetch (not client-hydrated): with real test data written to "HD Bridal Makeup," all 3 sections and their content appeared in the initial server-rendered response. After reverting the row to included_items: {}, suitable_for: {}, preparation_notes: NULL, a second raw fetch confirmed all 3 sections cleanly disappeared — no "no information available" placeholder anywhere — while the service name and price rendered correctly and unaffected.

13. Structured-Data Decision

Deliberately not mapped into JSON-LD. Kept as visible content only, per the instruction to prefer correct visible content over inventing unsupported schema.org properties.

14–16. Price/Duration Regression, RLS, Performance

No changes made to 3F.6's price/duration validation; the live test write/revert touched only the 3 new columns on the same row, leaving price, price_type, duration_minutes untouched. RLS is row-level, not column-level — services_owner_all's with_check: owns_beautician_profile(beautician_profile_id) covers the new columns automatically for every command (re-queried and confirmed unchanged live). service-page-query.server.ts already used select("*"), so the new columns flow through with zero new queries.

17–18. Add-Ons Audit & Package Relationship

Add-ons: documented only — no service_addons table built, consistent with the phase's scope limit. Packages: packages / package_services not touched in any way.
