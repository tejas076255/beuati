1–4. Architecture & Semantics

Audited the existing CRM filters — all local React state, no URL params. The new drill-down filter follows the exact same pattern: one more useState, intersected into the existing filtered-list logic as one additional constraint. Every predicate reads enquiry-level columns (lead_inquiries.source/utm_*/cta_location, lead_inquiry_services.service_tag) — never the customer-level leads.source/leads.service_id snapshot fields. A shared fetchOwnInquiriesInRange() helper is now used by both the Insights rollup and this drill-down so the two can never disagree.

5–6. Deduplication & Matched-Enquiry Context

Matches are grouped by lead_id server-side before reaching the CRM list. Live-verified: customer "Pooja Singh" has 2 enquiries both linked to "HD Bridal Makeup" — confirmed to collapse into exactly one result row with matchCount: 2, never a duplicated row.
Restructuring the lead detail dialog into a full multi-enquiry history view was explicitly deferred (a larger change, per the phase's own instruction). Instead, a small banner — "Matched via Insights · N matching enquiries · most recent: X, received Y" — was added to the existing dialog, satisfying the "at minimum" requirement without a redesign.

7–11. Range, Filters, Indicator, Back/Clear

The drill-down always reuses the exact insightsRange active when the row was clicked — no separate "locked range" state, no silent expansion to all-time. A dedicated banner shows the active insight filter, matching-customer count, and range, with its own Clear action — independent of the pre-existing status/attention-filter chips, which remain fully functional alongside it. Switching back to the Insights tab does not clear the drill-down filter, so a user can go back and forth without losing context.

12–13. Query Architecture & Security

Profile scoping is explicit (beautician_profile_id = bpId) on top of unchanged RLS — identical security posture to 3G.3B, live-verified to only ever reflect the one test profile's own data.
