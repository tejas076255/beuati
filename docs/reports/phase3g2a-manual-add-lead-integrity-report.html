1–3. Root Cause & Phone Validation

Root cause: createLead() had zero phone validation (any string accepted) and zero customer-matching logic — it unconditionally inserted a new leads row on every call. The exact same bug class fixed for the public form in 3G.1A, in a completely separate, never-touched code path.
Fixed: extracted the 3G.1A rule (digits-only, 8–15 length, country-agnostic) into a new shared src/lib/phone.ts. The public form's local duplicate was removed and now imports the same helper — the two paths can never diverge. Applied client-side to both Quick Add and Full Details schemas, and enforced authoritatively inside createLead() itself — a request bypassing the dialog still hits the same check.

4–6. Customer Matching & Form Parity

createLead() now normalizes the submitted phone, fetches this beautician's own leads (RLS-scoped), and compares normalized digits in application code. A match reuses the existing lead; no match falls through to the original insert path. Quick Add and Full Details both call the exact same createLead(), so both get identical behavior automatically — no second deduplication model.

7–8. Existing-Customer UX & Name Handling

On reuse, the success screen now shows "Existing customer found: {name}" / "New enquiry will be added to this customer" instead of the generic message — never shown as an error. Deliberately conservative: the customer's existing name and phone are never overwritten on reuse — only "current enquiry" snapshot fields refresh. This is intentionally more cautious than 3G.1A's public-form behavior, documented here as a deliberate scoped decision, not an inconsistency.

9–13. Source, Service History, Status & Follow-Up Preservation

Audited, not schema-changed: lead_inquiries has no inquiry-level source column. No column was added. Instead, each reuse-path enquiry's source is preserved durably in its activity note: "New enquiry added manually via {source}." — so WhatsApp-vs-Portfolio history stays visible without a new column.

Service history: unchanged — each enquiry keeps its own real service tag via existing lead_inquiry_services. Status: never touched by the reuse path — confirmed customer-level only, so a repeat manual enquiry can never reset an established pipeline stage. Follow-up: next_followup_at/next_followup_reason/last_contacted_at are never included in the reuse-path update.

14. Concurrency Finding

A genuine, low-probability race exists: two near-simultaneous requests for the same new phone could both find "no match" before either inserts. Per instruction, no new unique constraint was added (would be a real schema change). Documented residual limitation — recommend a future phase evaluate a profile-scoped, normalized-phone unique index if this proves to matter in practice.
