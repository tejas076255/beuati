1. Exact Runtime Error

TypeError: services.map is not a function — thrown synchronously inside GalleryPage's (and BeforeAfterPage's) render body, at the "Related service" dropdown code. An uncaught render-time exception, caught by TanStack Router's route error boundary and shown as the generic "This page didn't load. Something went wrong on our end."

2. Reproduction Sequence

  1. Visit /dashboard/gallery or /dashboard/before-after first in a session → works.
  2. Visit /dashboard/services at any point afterward → still works (that page reads its data defensively).
  3. Navigate back to Gallery or Before/After → crashes.
  4. A hard reload / fresh tab "fixes" it temporarily by starting the sequence over.

3–4. Root Cause & Why Login Temporarily Fixed It

router.tsx creates exactly one shared QueryClient for the entire SPA session. Three independent route files — Gallery, Before/After, Services — each declared their own listServicesFn but cached it under the identical literal key ["own-services"]. Until Phase 3F.8, all three returned the same flat-array shape. Phase 3F.8 repointed the Services page's query at listOwnServicesWithReadiness(), returning { services, readinessContext } — an object, not an array — without renamespacing its key. Once the Services page populated that shared slot with the object shape, Gallery/Before-After's next render called .map() directly on it.

Why login "fixed" it: a hard reload re-executes getRouter(), creating a brand-new, empty QueryClient — wiping the poisoned cache entry until the Services page is visited again in the fresh session.

5. Why Gallery and Before/After Were Affected

They're the only two routes that both (a) read the shared "own-services" key for their "Related service" dropdown and (b) call .map()/.find() on the result unconditionally during render, with no shape guard. The Services page's own optional chaining happened to absorb a wrong-shaped value without crashing — which is exactly why it looked "unaffected."
