1–2. Executive Verdict & Current Architecture

BeautyFolio runs on Lovable Cloud, Lovable's managed Supabase backend — a genuine, standard Postgres/Supabase instance accessed exclusively through the plain @supabase/supabase-js client. No proprietary Lovable database/auth/storage SDK exists anywhere in application code.

3–4. Live DB vs. Migration Files — Schema Drift

One real finding, self-corrected: services and packages already had a full UNIQUE (beautician_profile_id, slug) constraint since the very first migration — my own Phase 3F.4 audit missed this (inline in a CREATE TABLE block, didn't match my search pattern). My Phase 3F.4 migration added a second, functionally redundant partial index. Harmless — both now coexist, no conflict, just duplication. Documented, not fixed here per the audit-only instruction.

No other drift found across 26 tables, 11 functions, 18 triggers, 37 RLS policies, 11 enums — every live object traces to a migration file.

5. Migration-History Findings

Lovable Cloud doesn't expose the standard Supabase CLI migration-history table from this access path. Reconciled instead via exhaustive direct schema comparison (§3–4) — found fully consistent.

10–11. Auth Architecture & Migration Risk

  • Email/password only — no OAuth, no magic link found in the app
  • handle_new_user() trigger auto-creates profiles + default beautician role on signup
  • Role/ownership checks: user_roles table + has_role()/owns_beautician_profile() — no metadata-based role logic
Real risk found: profiles.auth_user_id has no database-level foreign key to auth.users.id — kept in sync only by the signup trigger. A future Auth migration needs explicit remapping. Supabase also doesn't support standard password-hash export — existing users would need a reset-password flow post-migration.
