A. Redundant Service Slug Index — Removed

services_beautician_profile_id_slug_key (original, full UNIQUE, present since the base migration) already provided identical protection to idx_services_bp_slug (Phase 3F.4's addition) — standard SQL treats every NULL as distinct, so the original already allowed unlimited NULL slugs while rejecting duplicate non-null pairs. Confirmed genuinely redundant, then dropped.

Verified after the drop: services_slug_format intact · all 5 existing service slugs unchanged · duplicate protection re-tested via a deliberately-failing, rolled-back insert against hd-bridal-makeup — correctly rejected with 23505 duplicate key value violates unique constraint "services_beautician_profile_id_slug_key" · post-check confirmed zero stray rows (count still exactly 1).

Matching migration created: supabase/migrations/20260824090000_drop_redundant_service_slug_index.sql

B. Dormant Service-Role Client — Audited, Kept As-Is

Repo-wide search confirmed supabaseAdmin/createSupabaseAdminClient (client.server.ts) has zero imports anywhere — application code, server functions, admin actions, build scripts, tests.

Decision: not deleted. The file is marked "automatically generated, do not edit directly" (Lovable-managed scaffold) — removing it risks silent regeneration or conflicting with Lovable's own codegen, for no real benefit: an unimported module with a lazy-init Proxy has zero runtime footprint whether or not the file exists. The actual goal — "the app doesn't depend on unused privileged code" — was already true. SUPABASE_SERVICE_ROLE_KEY was not rotated, exposed, or removed from Lovable Cloud.

C. Storage URL Migration Preparation — Created, Not Executed

New file: supabase/tooling/rewrite-storage-origin.sql

  • Dry-run mode first (read-only row-count + before/after value preview)
  • Only rewrites rows whose value currently starts with the exact old origin
  • Never touches video_url (YouTube/Instagram), storage_path, or any other column
  • Idempotent — a completed rewrite naturally excludes itself from the WHERE clause on re-run
  • Covers exactly the 3 columns identified in the Phase 3F.4A audit: beautician_profiles.profile_image_url, beautician_profiles.cover_image_url, portfolio_videos.thumbnail_url

Not run against any database — documentation/tooling only, ready for the day a real migration is approved.
