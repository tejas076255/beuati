1. Existing FK Architecture Discovered

portfolio_items.service_id / before_after_items.service_id already existed: nullable, ON DELETE SET NULL, item/pair-level (no per-image relationship). portfolio_videos has no service_id column at all.

Real ownership gap found: neither the RLS owner-write policy nor the foreign key validates that a linked service_id belongs to the same profile as the item — only that the item itself is owned and the service exists somewhere. A forged request could technically link Profile A's media to Profile B's service.

2. Database Changes

Zero changes to existing columns. One new migration prepared, mirroring the existing guard_beautician_profile_flags()/guard_review_verification() trigger pattern rather than inventing a new authorization mechanism — a BEFORE INSERT/UPDATE trigger on both tables rejecting any service_id not belonging to the row's own profile.

6. Service Ownership Protection

7. Service Deletion Behavior

Confirmed directly from the base migration SQL: service_id UUID REFERENCES public.services(id) ON DELETE SET NULL on both portfolio_items and before_after_items. Deleting a service never deletes Gallery or Before/After media — it only clears the link.
