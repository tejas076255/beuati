1–3. Phone Validation — Root Cause, Client & Server Fix

Root cause confirmed in the live function source: submit_lead()'s only phone check was coalesce(trim(_phone),'') = '' — non-empty, nothing else. "Singh", "Shukla", "Shah", "dd" were all accepted as valid phone values, with zero server-side format validation to catch a crafted request bypassing the browser.
Fixed at both layers. Client: isValidPhone() (digits-only, 8–15, country-agnostic) checked before the RPC call, with inline "Enter a valid phone number." — plus inputMode="tel"/autoComplete="tel" added. Server (authoritative): submit_lead() now normalizes via regexp_replace(_phone, '\D', '', 'g') and rejects anything outside 8–15 digits before any row is written. Live-verified in a rolled-back transaction: "Singh" and "123" both correctly rejected; "9000011111" and "+91 90000 11111" both correctly accepted.

4–8. Deduplication — Finding, Fix & Verification

Found: submit_lead() unconditionally INSERTed a new leads row on every call — the existing leads → lead_inquiries "one customer, many enquiries" architecture was never actually used for repeat customers. Every repeat enquiry silently became a new, unrelated customer.

Fixed: matches an existing lead within the same beautician_profile_id by normalized phone before deciding to insert vs. reuse. A legitimate repeat enquiry (different service/date) reuses the lead and adds a new lead_inquiries row, refreshing the lead's top-level snapshot. An identical phone+service+event-date resubmitted within 5 minutes is idempotent — no second inquiry row.

Live-verified in a single rolled-back transaction: two different services/dates from the same phone → 1 lead row + 2 inquiry rows. The exact-duplicate resubmit of one of those → still 1 lead + 2 inquiries (zero rows added by the duplicate). Double-submit protection at the client (in-flight disable + explicit "Send another request" reset, from Phase 3G.1) was already correct.
