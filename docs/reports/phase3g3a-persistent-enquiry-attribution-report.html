1–4. Audit & Architecture Decision

Live-inspected lead_inquiries/leads/lead_inquiry_services/lead_activities — zero attribution columns existed anywhere. leads.source was the only source-like field, customer-level only. Found a live bug during the audit: the "legacy" value availability_request — documented in lead-config.ts as pre-dating the canonical vocabulary — was still being actively written by the public form on every submission, instead of the canonical portfolio value. Fixed as part of this phase.

Attribution was placed on lead_inquiries, not leads — a customer can submit many enquiries from different channels over time, and leads' top-level fields are documented customer-identity/latest-snapshot fields never overwritten on reuse (Phase 3G.1A/3G.2A). Verified live: same phone, two campaigns, two independently-attributed inquiry rows (Test F).

8–13. Session Helper & Capture Behavior

src/lib/attribution.ts (new) — pure sessionStorage read/write, no UI logic. initAttribution() runs once per real page load (root mount, never on internal SPA navigation): a recognized UTM present → new campaign touch, overwrites utm_*/landing_path/referrer_host and clears any stale CTA; no UTM + nothing stored → captures landing/referrer only; no UTM + already stored → no-op, preserved. landing_path/conversion_path store pathname only, never query strings. referrer_host captures only an external hostname, never the full URL.

14–19. CTA Origin, submit_lead(), Manual Add Lead, leads.source

recordCtaClick(ctaLocation, profileSlug) is called from the existing shared CTA trackers on both the portfolio and service-detail pages — one integration point. Scoped by profile slug so a CTA click on one professional's page can never attribute an enquiry submitted on a different professional's page later in the same session (a correctness case surfaced during the audit, not explicit in the spec). Falls back to availability_section when no CTA preceded submission — never invents one.

submit_lead() gained 9 new optional parameters, all server-side sanitized (control characters stripped, length-capped, blanks nulled). Phone validation / customer dedup / 5-minute idempotency / cross-profile isolation are byte-for-byte unchanged. Manual Add Lead's insertInquiry() now writes source from the existing dropdown on all 3 call sites; UTM/landing/referrer/CTA stay NULL for manual entries, since none of that is genuinely known. leads.source is completely untouched.

20–28. Privacy, Security, RLS, CRM Display, Click-IDs

No customer name/phone/email/message/venue/address is ever written to an attribution column — confirmed by inspecting every test row. All 9 new RPC parameters are sanitized server-side (control characters stripped, length-capped, blanks nulled) before storage — never trusted from the browser alone.
RLS: the single lead_inquiries_owner_all policy is row-level (via lead_id → beautician_profile_id), not column-level — the 10 new columns inherit it automatically. No policy change needed or made.
CRM display: added one compact, read-only "Attribution" block to the lead detail dialog — shown only when at least one field has a value, each line conditional. No dashboard, no charts.
Click-IDs: confirmed zero gclid/gbraid/wbraid/fbclid handling anywhere — audited only, not implemented, per instruction.

30–32. Manual Tests, Limitations & Next Phase

Manual browser tests needed: open a portfolio URL with real UTM params, navigate to a service page, click a tracked CTA, submit the form, then confirm the dashboard's Attribution block shows the right channel/campaign/landing/CTA. Also verify the manual Add Lead dialog end-to-end.
