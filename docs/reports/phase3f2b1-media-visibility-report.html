1. Existing Visibility Architecture Discovered

portfolio_items.is_published and before_after_items.is_published already existed (item/pair-level, not per-image), defaulted to true, and the public query in portfolio-query.server.ts was already filtering on both — identical to how portfolio_videos was already filtered. The entire gap was UI-only: nothing in the dashboard ever set these columns to false. No duplicate visibility column (visible/active/is_visible) was needed or created.

4. Gallery Visibility Implementation

A real Switch component (not a checkbox/radio, per spec) labeled "Show on my portfolio", with contextual copy — "Visible to visitors on your public page" when on, "Hidden from your public page. Still saved and editable here" when off. Defaults to on for new items; preloads the item's current value when editing.

5. Before & After Visibility Implementation

One switch per pair — "Show this transformation on my portfolio" — matching the schema's pair-level storage. Because there is only one flag for both images, the "before visible, after hidden" inconsistent state the spec warned against is structurally impossible.

6. Public Rendering Behaviour

Unchanged code path — getPublishedPortfolioBySlug() was already excluding is_published: false rows before this task, so a hidden item simply stops being fetched server-side. It never reaches the mapper, the public page, or triggers an empty-section render (sections already only render when non-empty).

7. Structured-Data Exclusion Behaviour

Automatic, no code change required: buildImageObjects/buildVideoObjects in portfolio.$slug.tsx only iterate profile.gallery/profile.transformations, which are built from the already-filtered bundle. A hidden item cannot appear in ImageObject JSON-LD because it never enters the mapped profile at all.

8. RLS Verification

updatePortfolioItem/updateBeforeAfterItem write through the same owns_beautician_profile()-gated RLS policies already verified in Phase 3F.2B. No new write path was introduced — publish/hide is just another field on an already owner-scoped update, so cross-user visibility changes are rejected identically to any other field.
